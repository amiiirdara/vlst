The winner changes because **the entire blend input matrix is different**, not because Optuna vs stacking is inherently better.

In `tabpfn.ipynb`, standalone TabPFN is very strong (0.818). Meta-LR stacking (0.816) barely adds anything; Optuna is worse on test (0.785). When the TabPFN column is that strong, stacking mostly preserves it.

In `results.ipynb`, standalone TabPFN is weaker (0.765). Optuna learns weights `[59.9% tabpfn, 33.7% lgb, 6.5% rf]` and becomes the best blend in that notebook (0.779), but still below `tabpfn.ipynb`'s stacking because the TabPFN base score dropped ~0.05.

There is also a **methodological difference in stacking**:

- **`tabpfn.ipynb`**: honest nested OOF stacking (`stacking_oof_predict`) — meta-LR is refit inside each fold, so OOF scores are not leaked.
- **`results.ipynb`**: meta-LR is fit once on the full OOF matrix (`tabpfn_stacking_lr`), which is simpler but can be slightly optimistic on train/OOF.

So stacking wins in the dedicated TabPFN notebook; Optuna wins in the unified notebook — mainly because TabPFN inputs and base-learner probas differ.

## Why the notebooks disagree

Same split geometry (70/30, `random_state=42`, 28 test positives), but **not the same experimental environment**:

### 1. Different TabPFN feature matrix (main driver)

| | `tabpfn.ipynb` `load_raw()` | `results.ipynb` `df_to_raw_tabpfn()` |
|---|---|---|
| Stent column | Raw `"Stent type-SES"` → category codes | Canonicalized `stent_brand` |
| Cleaning | Minimal (drop IDs + leakage only) | Also `drop_duplicates`, PES/ZES/EVS coercion |
| TabPFN test PR-AUC | **0.818** | **0.765** |

Tree models are similar across notebooks (XGB ~0.67, LGB ~0.65–0.71), so this is **not a split bug** — it is TabPFN being sensitive to how categoricals are encoded.

### 2. Different evaluation roles

- **`results.ipynb`**: one cleaned table → scaled view (88 OHE features) for trees + raw view (81 features) for TabPFN; also holds out 15% cal slice from train for classical thresholds and advanced blends.
- **`tabpfn.ipynb`**: TabPFN-focused — full train for deployment-style test scores, dedicated blend section (§9), LOCO/SHAP on the §5 context model.

### 3. Threshold tuning differs (affects F1, not PR-AUC)

`results.ipynb` uses a coarser threshold grid (`linspace(0.02, 0.98, 97)`); `tabpfn.ipynb` uses a finer grid around TabPFN's high-probability regime (~0.88). That explains F1 gaps (0.755 vs 0.636) even when PR-AUC is closer.

### 4. Figure 2 mixes sources

`model_metrics.csv` is a **curated merge**:

```8:10:data/figures/model_metrics.csv
tabpfn_ref,tabpfn,test,0.818,0.991,0.755,0.800,0.714,,,tabpfn.ipynb
tabpfn_blend_optuna,tabpfn,test,0.779,0.991,0.686,0.647,0.722,,,results.ipynb
tabpfn_blend_stacking,tabpfn,test,0.816,0.992,0.750,0.750,0.750,,,tabpfn.ipynb
```

Panel A ranks `tabpfn_ref` and `tabpfn_blend_stacking` from `tabpfn.ipynb` next to `tabpfn`, `xgb`, `lgb` from `results.ipynb` — not a single fair horse race.

## Which results are more reliable?

**Depends on the claim:**

| Question | More reliable source | Why |
|---|---|---|
| TabPFN vs XGB/LGB on the **same rows & split** | **`results.ipynb`** | Unified protocol, dual views, same test set |
| Best TabPFN / blend under **TabPFN-native preprocessing** | **`tabpfn.ipynb`** | Matches TabPFN design (minimal encoding, no OHE) |
| LOCO, SHAP, blend ablations | **`tabpfn.ipynb`** | Dedicated, deeper analysis |
| A single leaderboard bar chart | **Neither as currently drawn** | Mixed sources inflate TabPFN vs trees |

**For a manuscript:** treat **`results.ipynb` as the primary cross-model comparison**, with the caveat that TabPFN there uses slightly more cleaning than the dedicated notebook. Treat **`tabpfn.ipynb` as the TabPFN reference run** for interpretability and blend work.

The suspicious pattern (OOF train PR-AUC **higher** in results but test **lower**) points to a **generalization shift from feature engineering**, not random noise:

| | OOF train PR-AUC | Test PR-AUC |
|---|---:|---:|
| `tabpfn.ipynb` | 0.569 | 0.818 |
| `results.ipynb` | 0.696 | 0.765 |

### Why report both?

1. **Transparency** — shows TabPFN scores move ~0.05 with stent-brand encoding alone; trees barely move.
2. **Avoid cherry-picking** — reporting only `tabpfn_ref` (0.818) without `tabpfn` (0.765) overstates TabPFN vs trees in a unified comparison.
3. **Different roles** — `tabpfn_ref` anchors LOCO/SHAP/blend work in `tabpfn.ipynb`; `tabpfn` is the fair anchor next to XGB/LGB in `results.ipynb`.

For the paper I'd suggest: **primary ranking from one notebook only** (preferably `results.ipynb`), and put `tabpfn_ref` in a sensitivity footnote or supplementary panel — not mixed in one bar chart without labeling the source split.
