### Your conceptual questions

- **Do many extra negatives (not used in training) “flatten” metrics?**  
  - **Recall** on the **original positives** is unchanged in principle: you only added **y = 0** rows, so **TP and FN on the old positives do not change**; recall is still TP / (TP + FN) on the same positive set.  
  - **Precision** can **fall** if the model flags some of the new negatives as positive: precision = TP / (TP + FP), and **FP can grow** when there are many more negatives at risk. If every new negative is predicted 0, precision stays the same.  
  - **Accuracy** often **rises** if the model is mostly right on negatives (many easy TNs), because the correct TN count grows faster than errors.

- **More or fewer false positives?**  
  - **Count of FPs** (predicted 1, true 0): usually **more** in absolute terms if the false-positive **rate** on negatives is fixed and you add many negatives.  
  - **FP rate among negatives** is the same idea as before; only the **denominator and raw FP count** scale with how many negatives you add.

## Why `@ t_f1_max(val)` can look worse than `@ threshold 0.5` (even on F1)

**`t_f1_max(val)` is chosen only on validation.** In your notebook, `best_threshold(y_val, p_val, t_grid, f1m)` picks a single threshold that maximizes **F1 on the validation set**. Every other line in the report (secondary holdout, abundant holdout, etc.) reuses **that same number**. It is **not** recomputed to maximize F1 on those splits.

So on holdout or abundant TN data you can easily get:

- **A different optimal threshold** than on val (shifted scores, different prevalence, many more negatives on abundant, etc.).
- **0.5** can sit closer to the “best” threshold for that split **by chance**, so F1 at 0.5 is higher than F1 at the val-optimal threshold.

That is normal: **optimizing on one split does not guarantee optimality on another.** It is the same reason val accuracy is not always a tight predictor of test accuracy.

A second, subtler effect: you are doing a **discrete search** on `t_grid` (e.g. steps of 0.01). The true best F1 threshold on val is on a grid point; on another split the best threshold might fall **between** grid points, so the val-chosen `t` can be slightly “off” elsewhere.

## What was the aim of still reporting `@ t_f1_max(val)` on holdout / abundant?

The goal is **not** to claim that this threshold always beats 0.5 on every split.

The goal is to show a **deployment-style, leakage-respecting operating point**:

1. **Fix the rule using only validation** (here: “use the threshold that maximized F1 on val”).
2. **Report what that rule does** on other splits **without** tuning the threshold on those splits.

So the comparison is:

- **0.5** — a fixed, conventional baseline (no tuning).
- **`t_f1_max(val)`** — “what you get if you actually tuned the decision threshold on val and then froze it,” evaluated elsewhere.

That answers a different question than “which threshold maximizes F1 on holdout?” (Answering the latter would require choosing `t` on holdout, which would **not** be a clean holdout evaluation.)

## Short takeaway

| View | Meaning |
|------|--------|
| **Val @ `t_f1_max(val)`** | By construction, F1 is (approximately) best on val among the grid. |
| **Holdout / abundant @ same `t`** | Can be worse than 0.5 — the val-optimal `t` need not be optimal there. |

So worse F1 at `t_f1_max(val)` than at 0.5 on abundant does **not** mean the pipeline is inconsistent; it means **val-tuned threshold ≠ best threshold for that other distribution of scores and labels.** Reporting both 0.5 and val-tuned thresholds is exactly what makes that visible instead of hiding it.

Here is the distinction in plain terms.

### Option A — **complement of train + test fold (deduped)**

- **What it is:** Take **every eligible row that was not used in training** for that ratio iteration, then **add** the rows from that iteration’s **stratified test fold**, and **dedupe** so the test fold is not counted twice if it is already inside the complement.
- **Effect:** You are trying to approximate “**everything left in the world after training**,” so the **negative prevalence is usually very high** (close to the real dataset if “eligible” is most of the table). Size can be **very large**.
- **Role:** Stress-tests the model under **near-natural class frequency**, but you must be strict about **what “not in train” means** (same row IDs, same pools as training) so you do not leak labels or duplicate union FP rows.

### Option B — **“natural prevalence” slice (what you picked)**

- **What it is:** You **build a holdout on purpose**: keep **all held-out positives and mined FPs** for that iteration, and add a **large but controlled TN sample** from the remaining pool so the split still looks **imbalanced like deployment**, but the evaluation set size stays **manageable**.
- **Effect:** Still **TN-heavy and realistic-feeling**, but you **choose how big** the TN cloud is (important for TabPFN limits, speed, and stable confusion matrices). It is **not** “literally every remaining row unless you set it that way.”
- **Role:** Mimics **operating conditions** (lots of easy negatives, rare positives) without necessarily materializing the **entire** complement of the database.

### One-line contrast

- **A:** “Evaluate on **(almost) all remaining data** + test fold,” subject to dedup and eligibility rules — often **huge**, prevalence **emerges** from what is left.  
- **B:** “Evaluate on a **designed deployment-like slab**” — **held-out positives/FPS + sampled abundant TNs** — prevalence is **engineered**, size **bounded**.

If you want both views, we can still do **matrix 1 = stratified test fold**, **matrix 2 = B** (your choice), and optionally add a third block later for an **A-style** full-complement eval when row counts allow.
